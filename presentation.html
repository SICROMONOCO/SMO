Introduction

Project Overview

The SysMon project is a Python-based system resource monitoring tool designed to track and analyze critical system metrics in real-time.

Assignment Objectives

Develop a comprehensive monitoring solution capable of tracking:

  • CPU Usage: Per-core utilization, frequency, and load averages
  • Memory Consumption: Physical RAM and swap space analysis
  • Disk I/O: Read/write operations and storage utilization
  • Network Activity: Interface statistics and traffic patterns
  • Process Metrics: Resource consumption by individual processes

Key Features

  • Real-time metric collection with configurable refresh intervals
  • Multi-interface support: Terminal UI (TUI), Web Dashboard, and CLI
  • JSONL-based structured logging for data persistence
  • Threshold-based alert system for proactive monitoring
  • Cross-platform compatibility (Linux, macOS, Windows)

Technical Stack

Python 3.8+ - Core programming language

psutil - System metrics collection library

socket - Network identification module

FastAPI - Web dashboard backend framework

Textual - Terminal-based user interface

Problem Statement

The Criticality of System Monitoring

In Linux server environments, continuous system monitoring is not optional—it's essential for maintaining service reliability, performance optimization, and security assurance.

Critical Challenges in Production Environments

1. Resource Exhaustion

Without monitoring, systems can experience CPU saturation, memory leaks, and disk space depletion, leading to service degradation or complete failure.

  • Out-of-Memory (OOM) killer terminates critical processes
  • Disk full conditions prevent logging and data writes
  • CPU throttling causes application timeouts

2. Performance Bottlenecks

Identifying performance issues becomes reactive rather than proactive, resulting in:

  • Increased mean time to resolution (MTTR)
  • User-reported issues instead of internal detection
  • Difficulty correlating symptoms with root causes

3. Security & Anomaly Detection

Abnormal resource consumption patterns may indicate:

  • Cryptocurrency miners running on compromised systems
  • DDoS attack traffic overwhelming network interfaces
  • Malware processes consuming excessive CPU/memory

Core Library: psutil

OS Kernel Interface

The psutil (process and system utilities) library provides a unified API for accessing system-level information across different operating systems.

Kernel Communication Mechanisms

Linux: Reads from /proc and /sys pseudo-filesystems

  • /proc/stat - CPU statistics
  • /proc/meminfo - Memory information
  • /proc/net/dev - Network interface stats
  • /proc/diskstats - Disk I/O counters

Windows: Uses Windows API calls

  • GetSystemInfo() - System information
  • GlobalMemoryStatusEx() - Memory status
  • GetDiskFreeSpaceEx() - Disk space

macOS: Leverages sysctl and libproc

  • sysctl() - Kernel parameters
  • proc_pidinfo() - Process information

System Call Abstraction

# Direct kernel interface (conceptual - Linux)
/proc/stat → CPU counters (user, system, idle, iowait)
/proc/meminfo → Memory metrics (MemTotal, MemFree, Buffers, Cached)
/proc/net/dev → Network interface statistics (bytes, packets, errors)

# psutil abstraction layer (cross-platform)
psutil.cpu_percent()       # Aggregates /proc/stat data
psutil.virtual_memory()    # Parses /proc/meminfo
psutil.net_io_counters()   # Processes /proc/net/dev

Key psutil Functions

Function Purpose Return Type
cpu_percent() CPU utilization percentage float
virtual_memory() Physical memory statistics svmem namedtuple
disk_usage() Disk space utilization sdiskusage namedtuple
net_io_counters() Network I/O statistics snetio namedtuple

Technical Insight

psutil bridges the gap between high-level Python code and low-level OS kernel operations, providing production-grade performance (C-compiled extensions) without sacrificing code clarity.

Host Identification

SysMon implements multiple layers of host identification for accurate system attribution in distributed monitoring environments.

Identification Hierarchy

1. Hostname (socket.gethostname())
   └─> FQDN resolution via DNS lookup (socket.getfqdn())
   
2. Network Interfaces (psutil.net_if_addrs())
   ├─> IPv4 addresses (AF_INET)
   ├─> IPv6 addresses (AF_INET6)
   └─> MAC addresses (AF_LINK / AF_PACKET)
   
3. Active Connections (psutil.net_connections())
   └─> TCP/UDP sockets with local/remote endpoints

Code Implementation

CPU Percentage Collection

Below is the actual implementation demonstrating how SysMon fetches CPU utilization:

import psutil
from typing import Dict, Any

class CPUMetrics:
    """Collect CPU performance metrics."""
    
    @staticmethod
    def get_cpu_percent() -> Dict[str, Any]:
        """
        Fetch CPU utilization percentage.
        
        Technical Details:
        - psutil.cpu_percent(interval=1) blocks for 1 second
        - Measures CPU usage by comparing /proc/stat counters
        - Calculates: (total_time - idle_time) / total_time * 100
        - Returns aggregate utilization across all cores
        
        Returns:
            dict: Metric with value, unit, type, and description
        """
        cpu_value = psutil.cpu_percent(interval=1, percpu=False)
        
        return {
            "value": round(cpu_value, 1),
            "unit": "%",
            "type": "dynamic",
            "refresh_interval": 2,
            "description": "Average CPU utilization"
        }
    
    @staticmethod
    def get_per_core_usage() -> Dict[str, Any]:
        """
        Get per-core CPU usage for detailed analysis.
        
        Returns:
            dict: Dictionary mapping core IDs to usage percentages
        """
        per_core = psutil.cpu_percent(interval=1, percpu=True)
        
        result = {}
        for i, usage in enumerate(per_core):
            result[f"core_{i}_usage"] = {
                "value": round(usage, 1),
                "unit": "%",
                "type": "dynamic",
                "refresh_interval": 2,
                "description": f"CPU usage for core {i}"
            }
        return result
    
    @staticmethod
    def get_cpu_frequency() -> Dict[str, Any]:
        """Get current CPU frequency in MHz."""
        freq = psutil.cpu_freq()
        return {
            "value": round(freq.current, 2),
            "unit": "MHz",
            "type": "dynamic",
            "description": "Current CPU frequency"
        }

Implementation Highlights

  • Blocking Interval: 1-second measurement window ensures accurate delta calculation
  • Precision: One decimal place balances accuracy and readability
  • Metadata: Each metric includes unit, type, and refresh interval for UI rendering
  • Type Hints: Python type annotations improve code clarity and IDE support

Deep Dive: Memory Management

Physical vs Swap Memory

SysMon distinguishes between two critical memory types that serve fundamentally different purposes in system operation.

Virtual Memory (Physical RAM)

Definition: Physical RAM (Random Access Memory) chips directly accessible by the CPU

Access Time: ~100 nanoseconds (extremely fast)

Use Case: Active processes, running applications, and frequently accessed data

Technology: DRAM (Dynamic RAM) - volatile memory

# Implementation from metrics/memory.py
import psutil

def get_virtual_memory():
    """Collect virtual (physical) memory statistics."""
    vmem = psutil.virtual_memory()
    return {
        "total": vmem.total,          # Total physical RAM installed
        "available": vmem.available,  # RAM available for new processes
        "used": vmem.used,            # RAM actively in use
        "percent": vmem.percent,      # Usage percentage
        "buffers": vmem.buffers,      # OS buffer cache
        "cached": vmem.cached         # Page cache for file I/O
    }

# Example output:
# {
#     "total": 16777216000,        # 16 GB
#     "available": 8388608000,     # 8 GB available
#     "used": 7516192768,          # ~7 GB in use
#     "percent": 44.8,
#     "buffers": 209715200,        # 200 MB
#     "cached": 3221225472         # 3 GB
# }

Swap Memory (Virtual Memory Extension)

Definition: Disk space designated for memory overflow when physical RAM is exhausted

Access Time: ~10 milliseconds (100,000x slower than RAM)

Use Case: Inactive memory pages paged out by the OS kernel

Technology: SSD or HDD partition/file

def get_swap_memory():
    """Collect swap memory statistics."""
    swap = psutil.swap_memory()
    return {
        "total": swap.total,    # Swap partition/file size
        "used": swap.used,      # Bytes written to swap
        "free": swap.free,      # Available swap space
        "percent": swap.percent # Swap usage percentage
    }

Technical Comparison

Aspect Physical Memory Swap Memory
Medium DRAM chips SSD/HDD partition
Speed 10-100 GB/s 200-500 MB/s (SSD)
Kernel Source /proc/meminfo /proc/swaps
Critical Threshold >90% = OOM risk >50% = thrashing

Monitoring Rationale

High swap usage indicates memory pressure (insufficient physical RAM), causing severe performance degradation through disk I/O. SysMon's alert system triggers warnings at configurable thresholds to prevent system slowdowns.

Challenges & Solutions

Challenge 1: Permission Errors

Problem

Accessing certain /proc files (particularly process-level information) requires elevated privileges. Running as non-root user causes PermissionError or AccessDenied exceptions.

psutil.AccessDenied: (pid=1234)
  File "/proc/1234/stat" requires root privileges

Solution: Graceful Degradation

import psutil
import logging

def collect_process_metrics(pid: int):
    """
    Collect process-level metrics with error handling.
    Falls back gracefully when permissions are insufficient.
    """
    try:
        process = psutil.Process(pid)
        return {
            "cpu_percent": process.cpu_percent(),
            "memory_info": process.memory_info(),
            "status": process.status()
        }
    except psutil.AccessDenied:
        logging.warning(f"Access denied for PID {pid}")
        return None  # Skip this process, continue monitoring
    except psutil.NoSuchProcess:
        logging.debug(f"Process {pid} no longer exists")
        return None

Result: The agent continues operation with reduced process-level detail rather than crashing. System-wide metrics remain accessible.

Challenge 2: Refresh Rate Synchronization

Problem

Different metrics have varying ideal collection frequencies:

  • CPU: 2 seconds (rapid changes)
  • Disk: 10 seconds (slower changes, expensive to query)
  • Memory: 5 seconds (moderate changes)

A single-threaded approach creates rigid, suboptimal timing.

Solution: Multi-Threaded Updaters

import threading
import time

class MetricUpdater(threading.Thread):
    """Independent thread for metric collection."""
    
    def __init__(self, metric_fn, interval):
        super().__init__(daemon=True)
        self.metric_fn = metric_fn
        self.interval = interval
        self.running = True
        
    def run(self):
        """Collection loop with configurable interval."""
        while self.running:
            try:
                self.metric_fn()
            except Exception as e:
                logging.error(f"Metric collection error: {e}")
            time.sleep(self.interval)

# Launch independent threads with optimized intervals
cpu_updater = MetricUpdater(collect_cpu, interval=2)
disk_updater = MetricUpdater(collect_disk, interval=10)
memory_updater = MetricUpdater(collect_memory, interval=5)

cpu_updater.start()
disk_updater.start()
memory_updater.start()

Result: Each metric collector runs independently with customized timing, minimizing system overhead while maximizing data freshness.

Challenge 3: Web Dashboard Data Staleness

Problem

WebSocket clients connecting when the log file is empty or very old receive "No data" indefinitely.

Solution: Tail-Follow Pattern with Retry

Web dashboard reads the last line of the JSONL log file and streams it via WebSocket. If the file is empty, shows a loading state with automatic retry logic.
