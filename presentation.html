Introduction

Project Overview

The SMO (System Monitoring & Orchestration) project is a comprehensive system resource monitoring tool built entirely in Python.

Assignment Context

Develop a Linux-compatible system monitoring solution that provides real-time insights into:

  • CPU utilization and performance metrics
  • Memory and swap usage tracking
  • Disk I/O and storage statistics
  • Network traffic analysis
  • Process-level resource consumption

Key Features

  • Real-time metric collection with configurable refresh intervals
  • Multiple interfaces: TUI (Terminal), Web Dashboard, and CLI
  • JSONL-based logging for data persistence
  • Alert system for threshold violations
  • Cross-platform compatibility (Linux, macOS, Windows)

Core Library: psutil & socket

psutil: OS Kernel Interface

The psutil library provides a unified API for accessing system-level information across different operating systems.

Kernel Communication Mechanisms

Linux: Reads from /proc and /sys pseudo-filesystems

Windows: Uses Windows API calls (GetSystemInfo, GlobalMemoryStatusEx)

macOS: Leverages sysctl and libproc

System Call Abstraction

# Direct kernel interface (conceptual)
/proc/stat → CPU counters (user, system, idle time)
/proc/meminfo → Memory metrics (MemTotal, MemFree, Buffers)
/proc/net/dev → Network interface statistics

# psutil abstraction layer
psutil.cpu_percent()  # Aggregates /proc/stat data
psutil.virtual_memory()  # Parses /proc/meminfo
psutil.net_io_counters()  # Processes /proc/net/dev

socket: Network Identification

The socket module enables hostname resolution and network interface discovery.

Key Functions

  • socket.gethostname(): Retrieves system hostname via gethostname() syscall
  • socket.gethostbyname(): Performs DNS resolution
  • psutil.net_if_addrs(): Enumerates network interfaces and their addresses (IPv4, IPv6, MAC)

Technical Insight

These libraries bridge the gap between high-level Python code and low-level OS kernel operations, providing production-grade performance without sacrificing code clarity.

Code Implementation

CPU Percentage Collection

Below is the actual implementation from metrics/cpu.py demonstrating how SMO fetches CPU utilization:

import psutil
from typing import Dict, Any

class CPUMetrics:
    """Collect CPU performance metrics."""
    
    @staticmethod
    def get_cpu_percent() -> Dict[str, Any]:
        """
        Fetch CPU utilization percentage.
        
        Technical Details:
        - psutil.cpu_percent(interval=1) blocks for 1 second
        - Measures CPU usage by comparing /proc/stat counters
        - Returns aggregate utilization across all cores
        
        Returns:
            dict: Metric with value, unit, type, and description
        """
        cpu_value = psutil.cpu_percent(interval=1, percpu=False)
        
        return {
            "value": round(cpu_value, 1),
            "unit": "%",
            "type": "dynamic",
            "refresh_interval": 2,
            "description": "Average CPU utilization"
        }
    
    @staticmethod
    def get_per_core_usage() -> Dict[str, Any]:
        """Get per-core CPU usage for detailed analysis."""
        per_core = psutil.cpu_percent(interval=1, percpu=True)
        
        result = {}
        for i, usage in enumerate(per_core):
            result[f"core_{i}_usage"] = {
                "value": round(usage, 1),
                "unit": "%",
                "type": "dynamic",
                "refresh_interval": 2,
                "description": f"CPU usage for core {i}"
            }
        return result

Key Implementation Details

  • Blocking Interval: 1-second measurement window for accuracy
  • Rounding: One decimal place balances precision and readability
  • Metadata: Each metric includes unit, type, and refresh interval for UI rendering

Deep Dive: Memory Management

Physical vs Swap Memory

SMO distinguishes between two critical memory types that serve fundamentally different purposes.

Virtual Memory (Physical RAM)

Definition: Physical RAM chips directly accessible by the CPU

Access Time: ~100 nanoseconds (extremely fast)

Use Case: Active processes and frequently accessed data

# Implementation from metrics/memory.py
def get_virtual_memory():
    vmem = psutil.virtual_memory()
    return {
        "total": vmem.total,          # Total physical RAM
        "available": vmem.available,  # RAM free for new processes
        "used": vmem.used,            # RAM in active use
        "percent": vmem.percent,      # Usage percentage
        "buffers": vmem.buffers,      # OS buffer cache
        "cached": vmem.cached         # Page cache
    }

Swap Memory (Virtual Memory Extension)

Definition: Disk space used when physical RAM is exhausted

Access Time: ~10 milliseconds (100,000x slower than RAM)

Use Case: Inactive memory pages (paged out by OS)

# Swap memory collection
def get_swap_memory():
    swap = psutil.swap_memory()
    return {
        "total": swap.total,    # Swap partition size
        "used": swap.used,      # Bytes written to swap
        "free": swap.free,      # Available swap space
        "percent": swap.percent # Swap usage percentage
    }

Technical Distinction

Aspect Physical Memory Swap Memory
Medium DRAM chips SSD/HDD partition
Speed 10-100 GB/s 200-500 MB/s
Kernel Location /proc/meminfo /proc/swaps
Critical Threshold >90% = OOM risk >50% = thrashing

Monitoring Rationale

High swap usage indicates memory pressure, causing performance degradation. SMO's alert system triggers warnings at configurable thresholds to prevent system slowdowns.

Challenges & Solutions

Challenge 1: Permission Errors

Problem

Accessing certain /proc files (e.g., process information) requires elevated privileges, causing PermissionError exceptions.

Solution: Graceful Degradation

try:
    process = psutil.Process(pid)
    cpu = process.cpu_percent()
except psutil.AccessDenied:
    # Fallback to aggregate metrics
    cpu = None  # Or skip this process
    logger.warning(f"Access denied for PID {pid}")

The agent continues operation with reduced process-level detail rather than crashing.

Challenge 2: Refresh Rate Synchronization

Problem

Different metrics have varying ideal collection frequencies (CPU: 2s, Disk: 10s), but a single-threaded approach creates rigid timing.

Solution: Multi-Threaded Updaters

class Updater(threading.Thread):
    def __init__(self, metric_fn, interval):
        self.metric_fn = metric_fn
        self.interval = interval
        
    def run(self):
        while self.running:
            self.metric_fn()
            time.sleep(self.interval)

# Launch independent threads
cpu_updater = Updater(collect_cpu, interval=2)
disk_updater = Updater(collect_disk, interval=10)
cpu_updater.start()
disk_updater.start()

Each metric collector runs on its own thread with customized timing, optimizing system overhead.

Challenge 3: Web Dashboard Data Staleness

Problem

WebSocket clients might connect when log file is empty or stale, showing "No data" indefinitely.

Solution: Tail-Follow Pattern

Web dashboard reads the last line of JSONL log file and streams it via WebSocket. If empty, shows loading state with retry logic.
